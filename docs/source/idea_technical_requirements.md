# Технічні вимоги та Архітектура: Термінал приймальника WMS 

## 1. Загальний опис та Архітектура
Система призначена для автоматизації процесів прийому, зважування, розподілу по вантажівках та розрахунку за ягоди (малина, полуниця, лохина) в умовах нестабільного інтернет-з'єднання на локації.

**Архітектурний патерн:** Local-First (Offline-First) гібрид. Усі критичні операції виконуються локально з подальшою фоновою синхронізацією.

**Технологічний стек:**
*   **Локальний термінал (Клієнт):** C++ (Qt/QML). 
    *   *C++ (Backend клієнта):* Забезпечує стабільну роботу 24/7, взаємодію з обладнанням, роботу з локальною БД та мережею без витоків пам'яті.
    *   *QML (UI клієнта):* Забезпечує реактивний, сучасний та зручний інтерфейс для оператора.
*   **Локальна база даних:** SQLite (для буферизації транзакцій офлайн).
*   **Хмарний бекенд (Майстер-вузол):** Go або Python (FastAPI) з використанням REST/gRPC.
*   **Основна база даних:** PostgreSQL 17.
*   **Веб-інтерфейс (для логіста/менеджменту):** SPA (React або Vue) для перегляду завантаженості фур, звітності та аналітики.

## 2. Ключовий функціонал C++ клієнта (Терміналу)

### 2.1 Hardware Layer (Робота з обладнанням)
*   **Драйвер ваг:** Фоновий демон (QThread), який слухає COM-порт за допомогою `QSerialPort`.
*   Парсинг безперервного потоку даних від електронних ваг.
*   Трансляція поточної ваги в UI (QML) через сигнали/слоти в реальному часі.

### 2.2 Offline-буфер (Sync Manager)
*   Усі записи (прийом товару, оплата, розподіл) спочатку записуються в локальну SQLite зі статусом `sync_status = 0`.
*   Фоновий потік (Sync Worker) постійно перевіряє доступність API (пінгує сервер).
*   При появі зв'язку дані відправляються батчами (пакетами).
*   **Ідемпотентність:** Усі транзакції генеруються з локальним UUID (v4), щоб уникнути дублювання записів при "морганні" мережі під час синхронізації.

### 2.3 Інтерфейс користувача (QML)
*   **Модуль Ідентифікації:** Пошук постачальника (за ID, прізвищем), відображення категорії ціни, вибір культури/сорту, введення кількості ящиків та ваги тари.
*   **Модуль Зважування:** Відображення поточної ваги з ваг (великим контрастним шрифтом), автоматичний розрахунок НЕТТО (Брутто мінус загальна вага тари).
*   **Модуль Розподілу (Логістика):** 
    *   Випадаючий список активних вантажівок.
    *   Візуальний прогрес-бар заповненості фури.
    *   Функціонал "Розщеплення": можливість розділити одну прийняту партію на дві різні вантажівки (наприклад, якщо перша заповнилась до кінця).
*   **Касовий Модуль:** Відображення поточного балансу/боргу постачальника, суми за поточну партію, поля для введення виданої готівки, розрахунок решти.

## 3. Проєктування бази даних та Бекенду

### 3.1 Основні сутності (Таблиці PostgreSQL)
1.  **Suppliers (Постачальники):** ID, ПІБ, категорія ціни, контакти.
2.  **Balances (Баланси):** Регістр накопичення для відстеження боргів або переплат постачальникам.
3.  **Trucks & Routes (Фури та Рейси):** Дані про автомобілі, максимальна місткість (в ящиках/кілограмах), статус рейсу.
4.  **Receipts (Чеки прийому):** UUID, дата, ID постачальника, ID ягоди, брутто, тара, нетто, ціна за кг, сума.
5.  **Cross-docking (Розподіл):** Зв'язок між Чеками та Рейсами (скільки ящиків/кг з конкретного чека пішло в конкретну фуру).
6.  **Payments (Оплати):** Історія видачі готівки або банківських переказів.

### 3.2 Вимоги до транзакцій та API
*   Використання суворих рівнів ізоляції транзакцій (`SERIALIZABLE` або `REPEATABLE READ`) на бекенді для уникнення розсинхронізації, особливо під час розщеплення партій між фурами.
*   API повинно підтримувати масове створення записів (Bulk Insert) для швидкої синхронізації локального офлайн-буфера з майстер-базою.
*   Централізоване керування цінами: оновлення прайсів приходить з бекенду на клієнт і кешується локально.
