# Berry WMS Terminal — робочий контекст для Claude

Спілкування з користувачем — українською. Код, ідентифікатори, коміти — англійською.

## Що це
Термінал приймальника ягід (малина, полуниця, лохина): прийом → зважування →
розподіл по вантажівках і на склад → розрахунок з постачальником. Offline-first. Особистий проєкт автора для реального
пункту (соло, без команди); почався як навчальний проєкт курсу ООП — усе про курс у розділі «Навчальний курс» нижче.

Первинні документи (не редагувати, лише довідково):
- `docs/source/idea_technical_requirements.md` — повне бачення автора (включно з хмарою/веб).
- `docs/source/course_requirements.md` — вимоги лектора курсу (див. «Навчальний курс»).

## Scope
**Зараз:** C++20 / Qt6 QML клієнт-термінал, локальна SQLite, ваги (ІЕ-04 і симулятор), друк чека,
синхронізація з **мінімальним сервером-заглушкою**.
**Пізніше:** Go/FastAPI бекенд, PostgreSQL 17, React/Vue SPA для логіста.
Не розширювати scope без запиту користувача.

## Прийняті рішення
- Соло-розробка. Терміналів на точці: 1–2 (архітектура не повинна ламатися при N).
- **Друк чека постачальнику** (рішення 30.10, замість термопринтера ESC/POS від 22.10):
  **звичайний принтер, один чек на сторінку A4** (можливо, згодом A5 — вирішиться на реальних спробах).
  Чек верстає й друкує **Qt** (`QPrinter` + `QPainter`, модуль PrintSupport, CUPS) — без зайвих залежностей;
  QR з UUID чека — **nayuki qrcodegen** (модулі QR малюємо самі).
- Гроші — `int64` копійки; вага — `int64` грами. Жодних float/double для грошей/ваги.
- Баланс не зберігається — обчислюється з append-only журналу `LedgerEntry`.
- Чеки незмінні; виправлення — сторно-записом.
- Ціна: **денна ціна на культуру**, задає оператор на терміналі; впродовж дня може змінюватися
  (наступні зважування отримують нову). Поля ціни на «Прийомі» немає (рішення 22.10): палета бере
  денну ціну, змінити — лише в «Оплатити» для всієї культури в чеку («вручну», на чеку не видно).
  Цінових категорій постачальників немає.
- **Сесія (робочий день):** відкривається оператором (~обід), називається датою відкриття,
  може тривати до ранку, закривається явно. Постачальники й борги спільні для всіх сесій
  (один журнал); вантажівки — свої в кожній сесії (можна «повторити вантажівку з учора»: той самий номер/ліміти,
  новий id). Закрити сесію можна лише коли для кожної незакритої вантажівки оператор вирішив: відправити
  (статистика поточної сесії) або перенести в наступну (той самий id — завантаження зберігається).
- **Склад:** як вантажівка, але не зникає між сесіями. З чека — на склад; зі складу — лише у вантажівку
  поточної сесії. Залишок за культурами обчислюється з журналу. Рідкісний продаж на місці —
  окрема «вантажівка» з відповідною назвою. Склад поки один; згодом можливі морозильні камери.
- **Оператори:** вибір зі списку + PIN (4–6 цифр) — підтвердження «хто», не захист (тому без хешу).
  PIN перевіряє UI; ядро отримує вже підтверджений `OperatorId`.
- **Закрита сесія** змінюється лише поправкою `Amendment {by, at, reason}` (пояснення обов'язкове);
  у журнал поправок пишеться й сама зміна.
- **Сесія спільна для точки** (рішення 28.10): один робочий день на всі термінали точки, не свій на кожен.
  Наслідки для sync (рішення 28.10, деталі — майбутній `docs/sync.md`):
  - сесія зберігається **фактами** (відкрито, ціна, вантажівка додана/відправлена/перенесена, закрито, поправка), як журнал;
  - **id сесії = UUIDv5(точка, дата відкриття)** — два термінали, що відкрили офлайн, сходяться; на точці одна
    сесія на дату; помилково закриту не відкривають заново, а виправляють поправкою;
  - **закрити спільну сесію — лише онлайн**: сервер підтверджує, що всі термінали синхронізовані й відкритих чеків нема;
  - **номери постачальників блоками за терміналом** (Т1 — 1000+, Т2 — 2000+), щоб офлайн-дублів не було;
  - термінал тягне не лише довідники, а й **чужі записи журналу** (баланси спільні); курсор pull — порядковий
    номер сервера, не час; у налаштуваннях термінала `pointId` + `terminalId`;
  - **сервер-заглушка — Python/FastAPI** (з неї може вирости бекенд), «дурний»: зберігає факти, видає номери;
    правила — в ядрі клієнта. Клієнт — Qt Network + JSON, outbox за `sync_status`.
  - **Порядок робіт:** `sessionId` + підсумки «Сесії» → друк чека → історія прийому, вантажівки, доплата
    (запит 10.11) → sync → звіти.
- **Чек і виплата знають свою сесію** (`sessionId`, рішення 28.10): належність до робочого дня — властивість запису,
  а не час створення (годинник може збитися, чек можуть внести пізніше). Виплата без відкритої сесії — без `sessionId`
  («поза сесією»). Старі записи — один раз за часом (міграція). Підсумки сесії рахуються за `sessionId`.
- **Забутий чек** (ягоду прийняли, чек не внесли до закриття) вноситься **в ту саму, вже закриту сесію** поправкою
  `Amendment {by, at, reason}`, а не в поточну.
- ID транзакцій — UUIDv7 (генерує клієнт), ідемпотентність на сервері за UUID.
- Sync: outbox (`sync_status`), батчі, сервер повертає прийняті UUID, retry з backoff;
  pull довідників і чужих записів журналу за курсором — порядковим номером сервера (див. «Сесія спільна для точки» вище).
- Офлайн-конфлікти (2 термінали вантажать одну вантажівку): факти приймаються, переповнення
  позначається для логіста, не відхиляється.
- Чек = кілька зважувань (`Weighing`, зазвичай палета) одного постачальника; культури важаться окремо,
  але йдуть в один чек. Вагу палети оператор вводить щоразу (0 — без палети).
- Постачальники від 2 до 1000+ ящиків. Режим розрахунку оператор обирає в чеку:
  роздріб — ціна відома, виплата на місці або пізніше (борг у журналі);
  опт — ціна невідома, лише вага, чек передається відповідальній людині (розрахунок поза терміналом).
  Друк чека обов'язковий в обох режимах + дані в системі.
- **Закриття чека (рішення 22.10, реалізовано):** дві дії.
  «Оплатити» (роздріб) — ціна грн/кг **одна на культуру в чеку**, підставлена **поточна** денна; якщо денної
  нема або треба змінити — вводиться тут, діє на всі палети культури в чеку; відмінна від денної — «вручну».
  **Виплата завжди одразу** на всю суму (готівка/переказ) — чек і `Payment` однією транзакцією; борг виникає
  лише через «Касу» (аванс) або з історії. Опція «Друкувати чек» (з інформацією про оплату).
  «Видати чек» (опт) — лише вага, без ціни, друк.
- **Кілька відкритих чеків одночасно** (один оператор): два великі постачальники розвантажуються
  по черзі, між ними — роздрібний з 2 ящиками. Кожне зважування йде в *активний* відкритий чек.
  `OpenReceipt` (чернетка) → `close(settlement)` → незмінний `Receipt` з тим самим UUID (видається
  при відкритті). Правила: палету можна розподілити, поки чек ще відкритий; відкриті чеки
  переживають перезапуск (кожне зважування зберігається одразу); у постачальника не більше одного
  відкритого чека (повторний вибір повертає до нього); сесію не можна закрити з відкритими чеками.
- Помилкове зважування не видаляється, а **анулюється**: рядок лишається (індекси для `Allocation`
  не зсуваються, слід помилки видно), але не рахується і не друкується; розподілене анулювати не можна.
  «Перенести в інший чек» = анулювати тут + додати там.
- Розподіл по вантажівках: цілою палетою (зважуванням) або N ящиків культури з чека (вага пропорційно).
- **Авторозподіл (рішення 22.10, реалізовано):** на «Прийомі» обирається поточна ціль (вантажівка
  сесії або склад). Записана палета одразу йде туди, куди пішла остання палета цієї культури **в цьому чеку**,
  інакше — в обрану ціль; оператор має явно бачити, куди вантажиться (рядок «Палета піде…» + «→» у чеку).
  Помилкову палету анулюють як завжди — розподіл знімається сторно-записом. Якщо у вантажівці не вистачає місця (ліміт у ящиках) — палета «підвішена» (нерозподілена).
  Вкладка «Розподіл» — для підвішених палет і відвантаження зі складу.
- **Ліміт вантажівки — лише в ящиках** (рішення 22.10); кг — довідково.
- Постачальника можна додати прямо з «Прийому» (пошук без збігів → «Додати»).
- **Культури — довідник у базі** (не `kCrops`): додаються оператором, бо змінюються протягом сезону;
  дублі на кшталт «Малина»/«малина » блокуються нормалізацією назви. Централізація — з сервером.
- Повноекранний режим — опція (F11 / меню ⋯ панелі), запам'ятовується.
- **Тара ящика** (рішення 28.10): на «Прийомі» поле одразу заповнене типовою тарою термінала (1,2 кг), змінюється
  в полі для іншого ящика; типове значення — меню ⋯ (`receiving/defaultBoxTare`). Порядок полів: ящиків, палета, тара,
  вага вручну, ціль.
- **Оболонка (рішення 28.10, макет https://claude.ai/artifact/55pwfPYLfRaVBFPMi6nLkD):** панель `AppBar` замість
  вкладок і футера; вкладки з іконками й клавішами **F5–F9**; чіпи ваг і сесії, оператор, меню ⋯.
- Ваги промислові, крок 200 або 500 г (налаштування). «Стабільно» = 3 однакові покази підряд
  (`StabilityDetector`, для симулятора).
- **Ваги на пункті (рішення 28.10, перевірено на пристрої 01.11):** ВН-2000-4, індикатор ІЕ-04 («Промприлад»),
  Max 2000 кг / Min 10 кг, фактичний крок табло 200 г (на шильдику e = 500 г). Кабель — оригінальний USB ↔ DB9
  (FTDI FT232R, `/dev/serial/by-id/usb-FTDI_FT232R_USB_UART_AN6UY90E-if00-port0`). **Протокол 1** (рішення 01.11):
  ваги самі шлють ~10 кадрів/с по 10 байтів (6 розрядів табло + статус: кома, стабільно, нуль, тара, мінус),
  адреса 01, **4800** 8N1; термінал лише читає, меню вагів не чіпаємо. Довідка й результати проби —
  `docs/hardware/scale-ie04.md`, сирий запис — `tests/data/ie04_protocol1_capture.bin`.
  Для справжніх ваг **стабільність = біт індикатора** (не 3 покази). Транспорт — **Qt SerialPort**.
  Нестабільну вагу оператор може підтвердити окремою клавішею (похибка в крок некритична);
  ручне введення маркується.
- SQLite: `journal_mode=WAL`, періодичний бекап.
- **Розгортання (рішення 24.11):** цільові — свіжі Fedora й Ubuntu (Qt ≥ 6.8: Fedora 42+, Ubuntu 26.04+; в Ubuntu 24.04
  Qt 6.4 — лише AppImage). Для пункту — **системні пакети `.rpm` + `.deb`** (правило udev дає порт ваг без `dialout`,
  оновлення разом із системою, з флешки — той самий файл); **AppImage** — запасний варіант на будь-який Linux;
  Flatpak (пісочниця заважає вагам/друку, база переїхала б) і Snap — ні. Windows — можливо пізніше (код переносний).
  Id застосунку — `io.github.isnazarii.BerryWms` (ярлик, іконка, `setDesktopFileName`); команда — `berry-wms`.
  База лишається в `~/.local/share/BerryWms/` — оновлення програми дані не чіпає.
  Правило udev (`uaccess`) лишається (рішення 24.11), але це зручність, а не єдиний шлях: на ПК пункту оператора
  все одно додають у `dialout` (інший кабель, не FTDI, чи запуск не з локального сеансу правило не покриває).
- **Ліцензія (рішення 24.11):** PolyForm Noncommercial 1.0.0 (`LICENSE.md`, рядок `Required Notice:` — автор). Код доступний
  для читання (source-available, **не** «open source» — так і не називати); комерційне використання, зокрема робота
  пункту, що належить не авторові, — окремою ліцензією автора. Ліцензії сторонніх частин — `THIRD_PARTY_NOTICES.md`
  (іде в пакет); нова бібліотека, шрифт чи іконки — дописати туди. Чужі внески — лише з передачею прав автору (CLA).
- **UI лишається на QML** (рішення 13.11, звіт експерименту — `docs/ui_qml_vs_widgets.md`; гілку `spike/history-ui` видалено 23.11): «Історія» на
  Qt Widgets + QSS — 250 рядків екрана + 284 нового спільного шару (і пастки на кшталт height-for-width у `QStackedWidget`);
  на спільних QML-компонентах — 107 замість 274 при тому самому вигляді. Надлишок UI-коду — від повторів, не від QML.

## Архітектура (шари)
```
core/   чистий C++20, БЕЗ Qt — доменна модель і правила (тестується GoogleTest)
        include/wms/*.h, src/*.cpp, namespace wms, бібліотека wms_core
infra/  wms_infra: обгортка SQLite (C API, амальгамація 3.51.2 через FetchContent, namespace wms::sqlite);
        + сховища, бекап; wms_serial — ваги (Qt SerialPort); wms_print — друк чека (Qt PrintSupport + qrcodegen);
        далі — HTTP-sync
ui/     QML-модуль BerryWms.Ui + тонкі Qt-адаптери (QObject/моделі), без бізнес-логіки
app/    main() — запуск QML, виконуваний файл wms_terminal
tests/  unit-тести, *_test.cpp, GoogleTest v1.17 через FetchContent; wms_core_tests, wms_infra_tests, wms_serial_tests, wms_print_tests
```
Залежності лише вниз: ui → infra → core. core не знає про Qt.

## Збірка
```bash
CM=~/.local/share/JetBrains/Toolbox/apps/clion/bin/cmake/linux/x64/bin
$CM/cmake -S . -B build -G Ninja && $CM/cmake --build build && $CM/ctest --test-dir build
```
Прапорці `-Wall -Wextra -Wpedantic -Wshadow` — збірка має бути без попереджень.

## Стиль коду
- Типи `PascalCase`, методи/змінні `camelCase`, поля `trailing_`, константи-функції `kopecks()`/`grams()`.
- `[[nodiscard]]` на геттерах/обчисленнях; `noexcept` де не кидає.
- Помилки програміста (некоректний конструктор) — `std::invalid_argument`;
  помилки вводу оператора — `validate()` повертає список повідомлень українською.
- Коментарі англійською, лише «чому», не «що».

Документація: `README.md` + `docs/` (architecture, domain, ui, development) — оновлювати разом зі змінами API.

## Робочий процес
- Тест-першим для `core/`: спершу тест, що падає, потім реалізація.
- Малі кроки, кожен крок — окремий коміт зі змістовним повідомленням.
- Користувач мусить розуміти весь код — пояснювати нетривіальні
  рішення, не генерувати великі шматки без пояснення.
- Не комітити без прохання користувача.

## Оточення
Дві машини автора; на обох збірка без попереджень і всі тести зелені.
- **Ноутбук (основний):** Fedora, CLion (cmake у PATH відсутній — використовується вбудований у CLion).
  Qt6 6.11: встановлені Gui/Quick/Qml/SerialPort/Sql/Test (+ драйвер QSQLITE). `sqlite-devel` не встановлено.
- **Друга машина (з 23.11):** Ubuntu 26.04, GCC 15, Qt 6.10.2 і cmake 4.2 з apt (проєкту досить Qt 6.8), без IDE.
  Збірка — `cmake` з PATH (команда з розділу «Збірка» без `$CM/`). Пакети: `git cmake ninja-build build-essential
  qt6-base-dev qt6-declarative-dev qt6-serialport-dev qt6-translations-l10n` + `qml6-module-qtquick*`/`qtqml*`.
  CUPS-заголовків нема (повідомлення cmake «Could NOT find Cups» — не заважає). Ваг і принтера нема — симулятор.
  Push — ключем `~/.ssh/id_ed25519` (fetch через HTTPS, push через SSH).
  Урок: GCC 15 одразу ламає висячі посилання на тимчасові (`X{...}.entries()`), які на Fedora «працювали».
- Порт ваг: права надаються **явно** (див. `docs/hardware/scale-ie04.md`, «Права на порт»). `pc` додано в групу `dialout` 01.11
