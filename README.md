# Berry WMS Terminal

Термінал приймальника ягід (малина, полуниця, лохина) для заготівельного пункту:
**прийом → зважування → розподіл по фурах і на склад → розрахунок з постачальником**.
Працює **офлайн-першим**: кожна операція фіксується локально як незмінний запис з UUIDv7
і згодом синхронізується з сервером.

## Навіщо це

У сезон на пункт за день приходять десятки постачальників — від пенсіонерки з двома ящиками
до фермерського господарства з тисячею. Приймальник має:

1. зважити кожну палету (брутто − тара ящиків − палета = нетто);
2. записати ціну, що діє саме зараз (вона може змінитися посеред дня);
3. одразу завантажити палету у фуру, що стоїть під рампою, або поставити на склад;
4. розрахуватися з постачальником на місці або записати борг;
5. роздрукувати чек.

Зв'язок на пункті ненадійний, тому термінал не може залежати від сервера: усе рахується
локально, а сервер лише збирає факти з одного чи кількох терміналів.

## Можливості

### Реалізовано в ядрі (`core/`, чистий C++20, покрито тестами)

- **Чек постачальника** з кількох зважувань (палет) різних культур; нетто =
  брутто − ящики × тара ящика − палета.
- **Кілька відкритих чеків одночасно**: два великі постачальники розвантажуються по черзі,
  між ними — роздрібний; кожне зважування йде в активний чек. У постачальника — не більше
  одного відкритого чека.
- **Дві дії закриття чека**: «Оплатити» (роздріб: одна ціна грн/кг на культуру в чеку, вся сума
  виплачується одразу) та «Видати чек» (опт: лише вага, розрахунок робить відповідальна особа поза
  терміналом).
- **Денні ціни** на культуру з історією змін; палети беруть денну ціну, а при «Оплатити» її можна
  змінити для всієї культури в чеку — така ціна позначається «вручну» всередині, але не видна на чеку.
- **Анулювання** помилкового зважування замість видалення (слід помилки лишається).
- **Розподіл** цілою палетою або N ящиків культури (вага ділиться пропорційно, без втрати грамів
  на округленні) — у фуру або на склад, у тому числі з ще відкритого чека.
- **Авторозподіл**: записана палета одразу йде туди, куди пішла попередня палета цієї культури в чеку,
  інакше — в обрану ціль; без місця у фурі палета «підвішена» й чекає ручного розподілу. Анулювання
  палети у фурі знімає її розподіл **сторно-записом** (`AllocationReversal`).
- **Склад**: залишок за культурами обчислюється з журналу; відвантаження зі складу у фуру.
- **Фури**: ліміт у ящиках (кг — довідково), заповненість у %, переповнення *позначається*, а не блокується
  (офлайн-конфлікт двох терміналів не губить фактів).
- **Сесія (робочий день)**: відкриття/закриття, фури сесії, «повторити фуру з учора»,
  перенесення незакритої фури в наступну сесію; закриття блокується з поясненням причин.
- **Поправки** в закритій сесії — лише з `Amendment {хто, коли, причина}` і журналом змін.
- **Журнал** append-only: баланс постачальника, завантаження фури, залишок складу — усе
  *обчислюється*, нічого не зберігається лічильником. Ідемпотентне додавання за UUID.
- **Ваги**: інтерфейс драйвера, симулятор і детектор стабільності (3 однакові покази поспіль).
  Справжні ваги — ВН-2000-4 з індикатором ІЕ-04 по RS-232; драйвер — коли буде доступ до ваг.
- **Оператори**: вибір зі списку + PIN 4–6 цифр; кожна виплата знає, хто видав гроші.
- **Довідники**: культури додаються оператором протягом сезону (дублі «Малина»/«малина » блокуються;
  культура з записами не видаляється, а ховається); новий постачальник — прямо з пошуку.

### Реалізовано в UI (`ui/`, Qt 6 / QML)

| Екран | Стан | Що вміє |
|---|---|---|
| Вхід оператора | ✅ | список операторів + PIN; без входу вкладки приховані |
| Сесія | ✅ | відкриття/закриття, ціни за культурами, додати / прибрати культуру, фури (додати / повторити / відправити / перенести), причини, чому сесію не можна закрити |
| Прийом | ✅ | відкриті чеки, пошук і додавання постачальника (F2), табло ваг зі стабільністю, культури кнопками, ціль і авторозподіл («Палета піде…»), рядки чека, анулювання, «Оплатити…» / «Видати чек…» |
| Розподіл | ✅ | чеки з нерозподіленим (відкриті й закриті, «підвішені» палети), палетою або N ящиків — у фуру чи на склад, завантаження фур і залишок складу |
| Склад | ✅ | залишок за культурами (між сесіями; від'ємний — червоним), відвантаження N ящиків у фуру сесії |
| Каса | ✅ | борги постачальників, виплата (готівка / переказ) з підтвердженням і залишком після неї, історія чеків і виплат |

Над екранами — панель: вкладки з іконками (F5–F9), стан ваг і сесії, оператор; масштаб інтерфейсу (100–175%,
свій на термінал), повноекранний режим (F11), тема й вихід — у меню ⋯.

## Стан проєкту

Альфа в розробці. Ядро закриває вимоги лабораторної 1 із запасом (23 класи, 5 ієрархій,
7 видів поліморфізму). Журнал, сесії, відкриті чеки й довідники (постачальники, оператори, культури) зберігаються
в локальній SQLite з бекапом; до появи сервера порожні довідники заповнюються демо-набором. Друк чека та
синхронізація — наступні етапи.

## Збірка й запуск

**Потрібно:** CMake ≥ 3.28, Ninja, компілятор з C++20 і `<format>` (GCC 13+ / Clang 17+),
Qt ≥ 6.8 (модулі Quick, QuickControls2; для українських стандартних кнопок Qt — переклади
`qt6-qttranslations`, необов'язково). GoogleTest і SQLite завантажуються автоматично (потрібна
мережа при першій конфігурації).

```bash
cmake -S . -B build -G Ninja
cmake --build build
ctest --test-dir build --output-on-failure   # 271 тест
./build/app/wms_terminal                      # термінал
```

Перевірка QML-файлів лінтером:

```bash
cmake --build build --target wms_ui_qmllint
```

Опція `-DWMS_BUILD_TESTS=OFF` вимикає збірку тестів. Збірка йде з
`-Wall -Wextra -Wpedantic -Wshadow` і має бути без попереджень.

**Демо-дані для входу:** оператори `Назарій` (PIN `1111`) і `Оксана` (PIN `2222`).
База — `~/.local/share/BerryWms/Berry WMS Terminal/terminal.db`; нова база отримує демо-сесію «вчора» й
трохи історії. Щоб почати з чистого аркуша — видалити файл; `WMS_DATABASE=:memory:` — запуск без сліду.
Поруч, у `backups/`, — копії бази (при запуску й закритті сесії, 30 останніх); як відновитися — [docs/ui.md](docs/ui.md).
На екрані «Прийом» кнопки симулятора ставлять на ваги палету або знімають її.

## Ключові інженерні рішення

- **Гроші й вага — цілі числа** (`int64` копійки / грами) у строго типізованому
  `Quantity<Tag>`: `Money + Weight` не компілюється, float-похибок немає.
- **Баланс не зберігається** — обчислюється з append-only журналу. Записи з іншого термінала
  зливаються в будь-якому порядку без втрат.
- **Записи незмінні** — помилки виправляються новим записом (анулювання, сторно), не редагуванням.
- **UUIDv7** генерує клієнт: сортуються за часом, ідемпотентність синхронізації за UUID.
- **Офлайн-конфлікти не відхиляються**: якщо два термінали переповнили фуру, обидва факти
  приймаються, переповнення показується логісту.
- **Помилки програміста vs помилки оператора**: некоректний конструктор кидає
  `std::invalid_argument`, а `validate()` повертає список зрозумілих повідомлень українською.

## Дорожня карта

1. ✅ Усі шість екранів альфи + прохід по UX.
2. `infra/`: SQLite ✅ журнал, сесії (архів), відкриті чеки переживають перезапуск, довідники
   (постачальники, оператори, культури) ✅, оператор у виплаті ✅, бекап ✅.
3. ✅ UX-зміни після огляду альфи: повноекранний режим, постачальник з «Прийому», довідник культур,
   ліміт фури в ящиках, авторозподіл, «Оплатити» / «Видати чек». Далі — розбір «примітивного» UI.
4. Друк чека на термопринтер 80 мм (ESC/POS) з QR-кодом UUID чека — лаба 3.
5. Синхронізація з мінімальним сервером-заглушкою: outbox, батчі, retry з backoff.
6. Драйвер реальних ваг ВН-2000-4 / ІЕ-04 через RS-232 (`SerialScaleDriver`, Qt SerialPort, протокол 0;
   стабільність — з біта індикатора). План — [docs/hardware/scale-ie04.md](docs/hardware/scale-ie04.md).

Поза курсом: повноцінний бекенд (Go/FastAPI + PostgreSQL) і веб-кабінет логіста.
