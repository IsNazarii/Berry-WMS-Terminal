# Berry WMS Terminal — робочий контекст для Claude

Спілкування з користувачем — українською. Код, ідентифікатори, коміти — англійською.

## Що це
Термінал приймальника ягід (малина, полуниця, лохина): прийом → зважування →
розподіл по фурах → розрахунок з постачальником. Offline-first. Один проєкт = особиста ідея
автора + навчальний проєкт курсу ООП (соло, без команди).

Первинні документи (не редагувати, лише довідково):
- `docs/source/idea_technical_requirements.md` — повне бачення автора (включно з хмарою/веб).
- `docs/source/course_requirements.md` — вимоги лектора (лаби 1–3, проєкт).

## Scope
**В межах курсу (до 13.11.2026):** C++20 / Qt6 QML клієнт-термінал, локальна SQLite,
симулятор ваг, друк чека, синхронізація з **мінімальним сервером-заглушкою**.
**Поза курсом (пізніше):** Go/FastAPI бекенд, PostgreSQL 17, React/Vue SPA для логіста.
Не розширювати scope без запиту користувача.

## Прийняті рішення
- Соло-розробка. Терміналів на точці: 1–2 (архітектура не повинна ламатися при N).
- **Лаба 3 = друк чека постачальнику.** Qt для цього заборонено (QPrinter/QPdfWriter не
  зараховуються). **Термопринтер 80 мм, ESC/POS** (рішення 22.10); QR з UUID чека — nayuki qrcodegen
  (або вбудований QR принтера). Конкретна модель ще не обрана; бажано цупкіший папір (не вимога).
- Гроші — `int64` копійки; вага — `int64` грами. Жодних float/double для грошей/ваги.
- Баланс не зберігається — обчислюється з append-only журналу `LedgerEntry`.
- Чеки незмінні; виправлення — сторно-записом.
- Ціна: **денна ціна на культуру**, задає оператор на терміналі; впродовж дня може змінюватися
  (наступні зважування отримують нову). Оператор може змінити ціну в конкретному зважуванні
  (разова надбавка) — всередині позначається «вручну», на друкованому чеку не видно.
  Зважування фіксує ціну на момент прийому. Цінових категорій постачальників немає.
- **Сесія (робочий день):** відкривається оператором (~обід), називається датою відкриття,
  може тривати до ранку, закривається явно. Постачальники й борги спільні для всіх сесій
  (один журнал); фури — свої в кожній сесії (можна «повторити фуру з учора»: той самий номер/ліміти,
  новий id). Закрити сесію можна лише коли для кожної незакритої фури оператор вирішив: відправити
  (статистика поточної сесії) або перенести в наступну (той самий id — завантаження зберігається).
- **Склад:** як фура, але не зникає між сесіями. З чека — на склад; зі складу — лише у фуру
  поточної сесії. Залишок за культурами обчислюється з журналу. Рідкісний продаж на місці —
  окрема «фура» з відповідною назвою. Склад поки один; згодом можливі морозильні камери.
- **Оператори:** вибір зі списку + PIN (4–6 цифр) — підтвердження «хто», не захист (тому без хешу).
  PIN перевіряє UI; ядро отримує вже підтверджений `OperatorId`.
- **Закрита сесія** змінюється лише поправкою `Amendment {by, at, reason}` (пояснення обов'язкове);
  у журнал поправок пишеться й сама зміна.
- ID транзакцій — UUIDv7 (генерує клієнт), ідемпотентність на сервері за UUID.
- Sync: outbox (`sync_status`), батчі, сервер повертає прийняті UUID, retry з backoff;
  pull довідників (постачальники, прайси, фури) за курсором `updated_since`.
- Офлайн-конфлікти (2 термінали вантажать одну фуру): факти приймаються, переповнення
  позначається для логіста, не відхиляється.
- Чек = кілька зважувань (`Weighing`, зазвичай палета) одного постачальника; культури важаться окремо,
  але йдуть в один чек. Вагу палети оператор вводить щоразу (0 — без палети).
- Постачальники від 2 до 1000+ ящиків. Режим розрахунку оператор обирає в чеку:
  роздріб — ціна відома, виплата на місці або пізніше (борг у журналі);
  опт — ціна невідома, лише вага, чек передається відповідальній людині (розрахунок поза терміналом).
  Друк чека обов'язковий в обох режимах + дані в системі.
- **Закриття чека (рішення 22.10, ще не реалізовано):** замість опису режимів — дві дії:
  «Оплатити» (роздріб) — тут ціна грн/кг **одна на культуру в чеку**, підставлена денна; якщо денної
  нема або треба змінити — вводиться тут, зміна діє на всі палети цієї культури в чеку й позначається
  «вручну»; опція «Друкувати чек» (з інформацією про оплату).
  «Видати чек» (опт) — лише вага, без ціни, друк.
- **Кілька відкритих чеків одночасно** (один оператор): два великі постачальники розвантажуються
  по черзі, між ними — роздрібний з 2 ящиками. Кожне зважування йде в *активний* відкритий чек.
  `OpenReceipt` (чернетка) → `close(settlement)` → незмінний `Receipt` з тим самим UUID (видається
  при відкритті). Правила: палету можна розподілити, поки чек ще відкритий; відкриті чеки
  переживають перезапуск (кожне зважування зберігається одразу); у постачальника не більше одного
  відкритого чека (повторний вибір повертає до нього); сесію не можна закрити з відкритими чеками.
- Помилкове зважування не видаляється, а **анулюється**: рядок лишається (індекси для `Allocation`
  не зсуваються, слід помилки видно), але не рахується і не друкується; розподілене анулювати не можна.
  «Перенести в інший чек» = анулювати тут + додати там.
- Розподіл по фурах: цілою палетою (зважуванням) або N ящиків культури з чека (вага пропорційно).
- **Авторозподіл (рішення 22.10, ще не реалізовано):** на «Прийомі» обирається поточна ціль (фура
  сесії або склад). Записана палета одразу йде туди, куди пішла остання палета цієї культури, інакше —
  в обрану ціль. Якщо у фурі не вистачає місця (ліміт у ящиках) — палета «підвішена» (нерозподілена).
  Вкладка «Розподіл» — для підвішених палет і відвантаження зі складу.
- **Ліміт фури — лише в ящиках** (рішення 22.10); кг — довідково.
- Постачальника можна додати прямо з «Прийому» (пошук без збігів → «Додати»).
- **Культури — довідник у базі** (не `kCrops`): додаються оператором, бо змінюються протягом сезону;
  дублі на кшталт «Малина»/«малина » блокуються нормалізацією назви. Централізація — з сервером.
- Повноекранний режим — опція (F11 / меню футера), запам'ятовується.
- Ваги промислові, крок 200 або 500 г (налаштування). «Стабільно» = 3 однакові покази підряд.
  Нестабільну вагу оператор може підтвердити окремою клавішею (похибка в крок некритична);
  ручне введення маркується.
- SQLite: `journal_mode=WAL`, періодичний бекап.

## Архітектура (шари)
```
core/   чистий C++20, БЕЗ Qt — доменна модель і правила (тестується GoogleTest)
        include/wms/*.h, src/*.cpp, namespace wms, бібліотека wms_core
infra/  wms_infra: обгортка SQLite (C API, амальгамація 3.51.2 через FetchContent, namespace wms::sqlite);
        далі — сховища, серійний порт, HTTP, друк чека — реалізації інтерфейсів з core
ui/     QML-модуль BerryWms.Ui + тонкі Qt-адаптери (QObject/моделі), без бізнес-логіки
app/    main() — запуск QML, виконуваний файл wms_terminal
tests/  unit-тести, *_test.cpp, GoogleTest v1.17 через FetchContent; wms_core_tests + wms_infra_tests
```
Залежності лише вниз: ui → infra → core. core не знає про Qt.

## Стиль коду
- Типи `PascalCase`, методи/змінні `camelCase`, поля `trailing_`, константи-функції `kopecks()`/`grams()`.
- `[[nodiscard]]` на геттерах/обчисленнях; `noexcept` де не кидає.
- Помилки програміста (некоректний конструктор) — `std::invalid_argument`;
  помилки вводу оператора — `validate()` повертає список повідомлень українською.
- Коментарі англійською, лише «чому», не «що».

## Стан і наступні кроки (оновлено 11.10.2026)
Ядро (`core/`): `Receipt` = постачальник + `Settlement` (`OnSite`/`HandedOver`) + `vector<Weighing>`
(`priceSource`: `DayPrice`/`Manual`; `cancelled` — рядок лишається, не рахується); `Payment`;
`OpenReceipt` (чек, що зважується: `add`/`cancel`, `validateClose`/`close(settlement)` → `Receipt` з тим самим
UUID і часом відкриття; для опту ціни обнуляються); `Allocation` (чек → `Destination` = фура | `ToWarehouse`;
`wholeWeighing` / `boxesOf`); `StockShipment` (склад → фура); `Truck` (id = UUID, статуси
`Loading`/`Departed`/`CarriedOver`; `TruckDetails {make, note}` — марка й вільний текст «водій / куди їде»,
необов'язкові, `repeatTruck`/`adoptTruck` їх копіюють) + `Cargo`; `DayPrices` (історія змін, `priceAt(crop, t)`);
`WorkDay` (сесія: дата відкриття, хто відкрив/закрив, ціни, фури, `validateClose`/`close`,
`repeatTruck`/`adoptTruck`; поправки в закритій сесії — перевантаження з `Amendment`, журнал `amendments()`;
відкриті чеки: `openReceipt(supplier)` — один на постачальника, `addWeighing(id, w, at)` сам бере денну ціну
на момент `at` (ручну не чіпає), `cancelWeighing(id, i, journal)`, `closeReceipt` → `Receipt`;
`validateClose` не пускає з відкритими чеками);
`Operator` (id, ім'я, PIN 4–6 цифр, лише `checkPin`); `parseMoney("85,50")` — ціна з вводу оператора (крапка або кома);
симулятор ваг + `StabilityDetector`; `Journal` — append-only: `balanceOf`, `loadOf` (з чеків і складу),
`stockOf`, `unallocatedOf`, `boxesOf`/`shipmentOf`, `validateAllocation`/`validateShipment` (для закритого чека
і для відкритого — палета йде у фуру ще під час розвантаження), `validateCancel` (розподілене не анулюється).
Відновлення відкритих чеків після перезапуску — конструктор `OpenReceipt` є, метод у `WorkDay` — разом зі SQLite.

UI (`ui/`, модуль `BerryWms.Ui`, статична бібліотека + `Q_IMPORT_QML_PLUGIN` у `app/main.cpp`):
синглтон `Terminal` (стан у пам'яті + запис кожної зміни в SQLite, міст QML → core), `SupplierListModel` (пошук),
`ScaleMonitor` (опитує `IScaleDriver` таймером). Екрани: Вхід оператора (список + PIN, без входу
вкладки приховані) ✅, Сесія ✅, Прийом ✅, Розподіл ✅, Склад ✅, Каса ✅. Вікно відкривається розгорнутим
(мін. 1024×600, цільові — ноутбуки); картки стискають текст (`elide`), щоб кнопки влазили. **Масштаб** — власний на термінал: меню у футері
(100–175%, типово 125%) → `QSettings` `ui/scale` → `main.cpp` ставить `QT_SCALE_FACTOR` до `QGuiApplication`
(діє після перезапуску; ручний `QT_SCALE_FACTOR` має пріоритет). Причина: GNOME «великий текст» бачать лише GTK-програми,
а при масштабі 100% на 15″ Full HD термінал замалий. Масштаб без перезапуску (`Theme.scale`) — можливо згодом,
коли зникнуть літеральні розміри з екранів.
`Terminal` тримає `std::optional<WorkDay>` (відкриває/закриває поточний оператор; назва — локальна дата з `QDate`).
Екран «Сесія»: відкриття, ціни за культурами (одна кнопка «Зберегти ціни» пише всі заповнені поля),
фури з завантаженням + «Відправити»/«Перенести», додати фуру (номер, марка, водій/куди, ліміти) або
повторити з минулої сесії, причини з `validateClose` видно одразу, закриття з підтвердженням.
Перенесені фури при відкритті приймаються автоматично (демо: `BI5678BB` «з учора» з палетою).
Закриті сесії лишаються в базі (архів), `previousTrucks_` — фури `lastClosed()`. Поправки в UI ще нема.
Культури — демо-список `kCrops` у `terminal.cpp` (каталог прийде з сервером).
Сигнали `Terminal`: `sessionChanged` (лише відкрито/закрито) → `pricesChanged`, `trucksChanged`;
`journalChanged` → `trucksChanged`; `receiptsChanged` (відкриті чеки/рядки/активний). Урок: `Repeater` над списком, що змінюється, перебудовує рядки й
стирає введений текст — модель рядків має бути сталою (`crops`), змінні дані — окремою властивістю (`prices`).
Перевірка QML: ціль `wms_ui_qmllint` (на кожному кроці).
Прохід по UX ✅: переклад Qt `qt_uk` у `main.cpp` («Скасувати»); `NoSessionNotice` з «До сесії» на Прийомі/Розподілі;
причини закриття сесії — кольором попередження; підказка `FieldCaption` зникає, коли не влазить (`truncated`);
головна кнопка «Прийому» не обрізається (`minimumWidth: implicitWidth`, коротший текст при ширині < 520).
Запуск без вікна: `WMS_DATABASE=:memory: QT_FORCE_STDERR_LOGGING=1 QT_QPA_PLATFORM=offscreen timeout 3 build/app/wms_terminal` —
без `QT_FORCE_STDERR_LOGGING` попередження йдуть у journald, а `console.log` (debug) у Fedora вимкнено.
**Стиль:** HTML-макет «Прийому» → синглтон
`ui/style/Theme.qml` (токени, світла/темна, шрифт Onest з `ui/style/fonts/` + табличні цифри). В екранах жодних літеральних кольорів/розмірів — лише `Theme.*`.
Власний стиль контролів — модуль `BerryWms.Style` (`ui/style/`, шаблони `QtQuick.Templates`, запасний — Basic),
вмикається в `main.cpp` (`QQuickStyle::setStyle`). Кнопка `highlighted` = одна головна дія панелі; `WarningButton` — ризикована дія поруч.

Екран «Сесія» — у стилі «Прийому» ✅: ціни дня (панель зліва), фури таблицею з голими числами
(`truckInfo`: `loadBoxes`/`loadKg`/`limitBoxes`/`limitKg`), нова фура й «повторити з минулої» — діалог
«Додати фуру…». Спільні підписи — файли `SectionCaption.qml`, `FieldCaption.qml`, `ColumnHeader.qml`.
Екран «Розподіл» — у стилі «Прийому» ✅: таблиця палет (№ · культура · ящ. · нетто · де), смуга «Куди», фури з
`loadBoxes`/`limitBoxes`/`loadKg`/`limitKg`. `describeCargo` (рядки UI) тепер у екранному форматі (`2 000,0 кг`). Урок: колонки таблиці

не збігається із заголовком. Знімок екрана без вікна: тимчасово в `main.cpp` `grabWindow().save()` за таймером.

Екран «Прийом» (`ReceivingScreen.qml`, розкладка за макетом): зліва відкриті чеки (сума або «порожній») +
«Новий чек · F2» → `SupplierPicker.qml` (спливний пошук, Enter бере єдиний збіг); по центру табло-прилад
(`display` — лише число, лампи СТАБ/НУЛЬ/БРУТТО), культури великими кнопками (до 5, спершу з денною ціною, решта
в «Ще ▾» — якщо культур > 6), поля двома групами (ціна/тара ящика; ящики/палета/вага вручну — підписи першим
рядком `GridLayout`, підказка в рядку підпису), «Записати · Enter» лише зі стабільною або ручною вагою,
«Прийняти нестабільну» — `WarningButton`; справа чек таблицею (№ · культура · ящ. · нетто · ціна · сума · ✕;
ручне — бурштиновим з `*`, брутто/тара в підказці, анульовані закреслені, «✕» показує `validateCancel`),
підсумок `activeSummary`, «Закрити чек…» → роздріб/опт з причинами з `validateClose`. `Terminal` тримає UUID
активного чека (не вказівник); постачальник у футері = постачальник активного чека. Після запису культура й
тара ящика лишаються, решта полів чиститься. Числа на екрані — `display_format.h` (`142,6`, `8 823,00`; кома,
вузькі пробіли); ядро форматує по-старому (`12.345 кг`) — для повідомлень. Урок: назва властивості на
`on` + велика літера = обробник сигналу (токен `onAccent` → `textOnAccent`).
Ваги вводяться в кг через `parseWeight` (ядро, спільний з `parseMoney` розбір `parseFixed`).

Екран «Розподіл» (`AllocationScreen.qml`): зліва чеки з нерозподіленим (`allocationSources`: відкриті сесії,
потім закриті з `Journal::waitingForAllocation`), по центру рядки обраного чека («Палету →» або «у фурі …»/«на складі»
з `Journal::destinationOf`) і «Ящиками» по культурах із залишком, справа місця (`destinations`: фури в статусі
`Loading` зі смугою заповнення + «Склад» із залишком). Обраний чек розподілу (`allocationReceiptId_`) окремий від
активного чека прийому; обране місце тримає QML, `Terminal::destinationFor` перевіряє фуру. Відкритий/закритий
чек — `std::variant<const OpenReceipt*, const Receipt*>` + `std::visit` з перевантаженими `unallocated()`/`check()`.
Сигнал `allocationChanged` ← `trucksChanged`, `receiptsChanged`. `Journal::findReceipt` тепер публічний.

Екрани «Склад» і «Каса» — у стилі «Прийому» ✅ (усі шість екранів переведені). `stock` віддає голі числа
(`boxes`, `kg`, `empty`); суми «Каси» (`debtors`, `cashBalance`, `cashHistory.effect`, `balanceAfter`) — `hryvniasText`
(мінус — U+2212, у QML перевірка `startsWith("\u2212")`). Діалог виплати — власні кнопки «Виплатити»/«Скасувати».
Екран «Склад» (`WarehouseScreen.qml`): залишок `stock` за всіма культурами (видно й без сесії; від'ємний —
червоним), «Відвантажити» N ящиків у фуру сесії (`shipFromStock` → `shipmentOf`/`validateShipment`; ціль «склад»
відхиляється). Фури — `destinations` без складу (фільтр у QML). Демо: палета полуниці Мельник на складі з учора.

Екран «Каса» (`CashScreen.qml`, працює й без сесії): зліва `debtors` (ненульові баланси, переплачені — червоним),
F2 → `SupplierPicker`; по центру обраний `cashSupplierId` (окремий від активного чека), сума + «Весь борг»
(`cashDebtInput`), готівка/переказ, підтвердження з `balanceAfter` (переплата дозволена — аванс, з попередженням);
справа `cashHistory` з `Journal::historyOf` (чеки й виплати за часом; текст — віртуальний `describe()`,
сума — `balanceEffect()`). Сигнал `cashChanged` ← `journalChanged`. Під виплатою в історії — «видав(ла): ім'я» (`Payment::paidBy`).

Наступні кроки (кожен — окремий коміт, ядро тест-першим):
1. SQLite (`infra/`), обрано прямий C API `sqlite3` (не Qt Sql). Кроки:
   a) ✅ обгортка `sqlite::Database`/`Statement`/`ScopedTransaction`/`Error` (WAL, foreign_keys, без `double`);
   b) ✅ схема (`migrateSchema`, `PRAGMA user_version`, STRICT, час у нс, enum текстом) + `JournalStore` (core) →
      `SqliteJournalStore` (infra): `save(...)` → `false` для наявного UUID, `load()` → `Journal`;
   c) ✅ `WorkDay` має `id` + `restore(WorkDayRecord)`; `SessionStore` (`save`/`current`/`lastClosed`) →
      `SqliteSessionStore` (міграція 2, знімок сесії з відкритими чеками); `ScopedTransaction` на `SAVEPOINT`
      (вкладається); `Terminal` пише кожну зміну (`saveSession()`, `record(x)`; закриття чека — одна зовнішня
      транзакція). База: `~/.local/share/BerryWms/Berry WMS Terminal/terminal.db`, `WMS_DATABASE` перевизначає
      (`:memory:` — без сліду); демо (`seedDemoData`) лише в нову базу. Після перезапуску активного чека нема.
   d) ✅ довідники: `Repository<T>` (core) → `SqliteRepository<T>` (міграція 3, upsert за id; явна інстанціація
      для `Supplier`/`Operator`); `Operator::pinForStorage()`; `Terminal` читає їх з бази, порожня таблиця
      засівається демо-набором (`loadOrSeed`) — так і стара база отримує довідники;
   e) ✅ `Payment::paidBy` (обов'язковий, `invalid_argument` для ≤ 0); міграція 4 перебудовує `payment`
      (старі рядки → оператор 1); `Terminal::pay` бере поточного оператора;
   f) ✅ бекап: `Database::backupTo` (`VACUUM INTO`) + `backupDatabase` (infra, ротація `keep`); `Terminal::backup()`
      при запуску й після закриття сесії → `backups/` поруч із базою, 30 копій; помилка — лише `qWarning`.
   Етап SQLite закрито.
2. UX-зміни від 22.10 (порядок): a) повноекранний режим; b) новий постачальник з «Прийому»;
   c) довідник культур у базі; d) ліміт фури лише в ящиках; e) авторозподіл з «Прийому» + підвішені палети;
   f) закриття чека «Оплатити»/«Видати чек» з ціною на культуру; g) розбір «примітивного» UI зі скріншотами.
3. Ваги RS-232 (коли буде доступ), друк чека ESC/POS (лаба 3), sync.
- Історії руху складу (прихід/відвантаження) в UI нема — `Journal` не віддає записи; за потреби — запит у ядрі.
- Повідомлення ядра про розподіл містять код культури (`raspberry`), а не назву — назви живуть у UI (`kCrops`).
- ❓ Захист від подвійного запису тієї самої палети (вимагати повернення ваг до нуля між зважуваннями) —

## Відкриті питання
- Конкретна модель термопринтера 80 мм?
- Модель ваг і їх протокол по COM-порту? Є кабель USB↔RS-232; доступ до ваг — найближчим часом
  (план: утиліта-сніфер сирих байтів → `SerialScaleDriver`).
- UI «відчувається примітивно» — користувач не може назвати причину; потрібен розбір зі скріншотами.
